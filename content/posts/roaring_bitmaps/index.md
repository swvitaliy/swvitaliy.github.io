Не так давно мне довелось попробовать работать с ClickHouse. В частности, с такой ее фичей, как Roaring Bitmaps. Остался от данного опыта под приятным впечатлением, и, в тоже время, заинтеревовался, за счет чего roaring bitmaps работают наслолько быстро. Решил разобрать, как же реализована эта структура данных и провести сравнение производительности работы с включенными и выключенными оптимизациями.

### Для чего нужен roaring bitmaps?

Почему бы просто не хранить в bitmaps/arrays?

При хранении множества в bitmap нам заранее нужно выделить большой объем памяти под все потенциально возможные значения. При наличии миллионов значений мы получим, что каждое такое множество должно иметь размер в мегабайты. Если это будут разреженные данные, то большая часть этих данных будет пустой.

При хранении множества в array нам нужно обращаться к элементу через бинарный поиск. Так же для пересечения 2-х массивов (при мерже) нужно линейно пройтись по ним в общем случае.

Зачастую, мы заранее не можем сказать какой характер данных поступит на вход и, соответственно, нельзя выбрать одну из 2-х этих структур для оптимальной работы. Для таких случаев и придумана такая гибридная структура данных как roaring bitmap.


## Описание структуры данных roaring bitmaps

roaring bitmaps хранит 32-х битные значения.

Основная идея данной структуры данных - поделить весь диапазон нзначений на небольшие "корзинки", каждая из которых оптимизирована по характеру данных, которые в них содержатся. 

Для большого набора последовательных значений используется такая оптимизация, как **run-контейнеры**, которая дает существенный прирост в производительности на данных, в которых есть последовательные цепочки. Небольшой прирост в производительности дает векторизация - по моим замерам до 1.5 раз на операцию `And`.

Поверх roaring bitmaps навешивают операции rank и select со своими оптимизациями. Например, для select изпользуется кеш в виде массива префиксных сумм.

При создании структуры выделяется таблица ключей контейнеров. В ней в качестве индекса используются верхние биты занчения (64К значений). Таким образом, в корзинке, которая по этому ключу доступна, так же воможно хранить не более 64К элементов из из нижних 16 бит переданного 32-х битного числа.  

Контейнер может быть одного из трех типов. По умолчанию используется **array** - отсортированный массив 16-битных значений, занимающий `2*N` байт. Как только число элементов превышает 4096, контейнер превращается в **bitmap** - 8192 байта (65536 бит) фиксированного размера. Порог 4096 - это точка безубыточности: `4096 * 2 = 8192`, то есть ровно размер bitmap. Дальше array только растет, а bitmap - нет. При удалении элементов работает обратный переход: как только в bitmap остается 4096 или меньше элементов, он снова становится array. Третий тип - **run**-контейнер - описан ниже.

При добавлении/удалении/проверке на принадлежность необходимо выполнить поиск значения. При поиске значения мы сначала ищем в таблице ключей по верхним битам числа. Затем, выполняем поиск в контейнере по младщим битам. В зависимости от типа контейнера или выполняем обращение по битмапе по ключу или выполняем бин поиск в массиве или в массиве интервалов (для run контейнеров).

### Run-container оптимизация

На этапе `run optimize`, выполняется замена bitmap и array на run-контейнеры.

Run-container - это RLE, массив интервалов, каждый элемент которого содержит начальный индекс и длину интервала.

Выгоды от такого способа представления множества довольно очевидны - если чисел в контейнере много, но они образуют небольшое число серий, мы получим оптимизацию по памяти. Важно, что критерий именно число серий, а не плотность: плотный контейнер с чередующимися битами (1, 3, 5, 7, ...) дает максимум серий, и run для него хуже и array, и bitmap. Если же количество интервалов невелико, то и бинарный поиск будет состоять из всего лишь нескольких проверок. Поэтому даже переход от bitmap контейнера к run контейнеру не даст заметной просадки в производительности.

При вставке одиночных элементов run-container не создается: новый контейнер всегда начинается как array, и превращение в run происходит только явным вызовом `runOptimize`. Исключение - вставка диапазона (`addRange` в CRoaring): она сразу создает run-контейнер, поскольку диапазон и есть одна серия. Если же элемент добавляется в уже существующий run-контейнер, он остается run-контейнером - библиотека просто расширяет или расщепляет серию. Сам шаг `runOptimize` (замену "стандартных" контейнеров на run-container) нужно делать периодически в бекграунде и перед сериализацией.

![](content/posts/roaring_bitmaps/rbm_choose2.svg)

Для замены bitmap и array на run-container нужно сравнить размер текущего контейнера и полученного контейнера с интервалами. Для этого нужно сначала посчитать R - число последовательно идущих серий значений. Каждый интервал содержит 2 числа - начальный индекс и длину этого интервала. Поэтому, размер контейнера с интервалами будет `4*R`  - 2 16-ти битных числа. Размер же изначального контейнера будет равен `2*N`. Если `4*R` меньше, чем `2*N`, то конвертируем в run контейнер.

Для подсчета `R` в bitmap можно использовать popcnt. Но может быть несколько подряд идущих ноликов, а нам нужно посчитать только те нолики, которые идут перед серией из единиц. Другими словами - число серий равно числу позиций, где серия начинается, то есть где бит равен 1, а предыдущий (младший) бит равен 0. Для этого мы считаем сумму по каждому слову в bitmap контейнере `popcnt(w & ~(w<<1))`.

## Roaring bitmaps operations

Для операций And/Or/NotAnd/Xor 2-х roaring bitmaps сначала применяется merge на отсортивованных массивах ключей, что довольно удобно.

```go
// And returns the intersection of b and other.
func (b *Bitmap) And(other *Bitmap) *Bitmap {
	out := &Bitmap{}
	i, j := 0, 0
	for i < len(b.keys) && j < len(other.keys) {
		switch {
		case b.keys[i] < other.keys[j]:
			i++
		case b.keys[i] > other.keys[j]:
			j++
		default:
			out.appendContainer(b.keys[i], andContainers(b.conts[i], other.conts[j]))
			i++
			j++
		}
	}
	return out
}

// Or returns the union of b and other.
func (b *Bitmap) Or(other *Bitmap) *Bitmap {
	out := &Bitmap{}
	i, j := 0, 0
	for i < len(b.keys) && j < len(other.keys) {
		switch {
		case b.keys[i] < other.keys[j]:
			out.appendContainer(b.keys[i], b.conts[i].clone())
			i++
		case b.keys[i] > other.keys[j]:
			out.appendContainer(other.keys[j], other.conts[j].clone())
			j++
		default:
			out.appendContainer(b.keys[i], orContainers(b.conts[i], other.conts[j]))
			i++
			j++
		}
	}
	out.appendRest(b, i)
	out.appendRest(other, j)
	return out

```

В методе `And` в результат добавляется контейнер только тогда, когда совпадают ключи (верхние биты). Тут нужно пересечь 2 множества и, если верхние биты не пересекаются, то нам такие контейнеры не интересны.

Операции `andContainers` и `orContainers` представляют из себя объединение 2-х контейнеров и могут применятся для пар контейнеров. 

В качастве примера рассмотрим пересечение контейнеров `andContainers`:
1. интервал & интервал - пересечение массивов интервалов
2. интервал & массив - массив и интервалы обходятся одним проходом: для каждого значения массива индекс интервала сдвигается вперёд, пока текущий интервал заканчивается раньше значения. Значение попадает в результат, если оказалось внутри текущего интервала. Буфер под результат выделяется по кардинальности массива, результат всегда array-контейнер.
3. 

Многие операции реализованы крайне интересно - с применением "битовой магии". Большая часть из них имеет векторные оптимизации. Более подробно про реализацию битовых операций над векторами постараюсь написать в следующем посте (думаю, этот и так оказался довольно объемным).

После многих операций применяется метод `normalize`. В зависимости от количества элементов в контейнере он выполняет переход из одного контейнера в другой.

```go
func (c *container) normalize() *container {
	if c == nil || c.card == 0 {
		return nil
	}

	switch c.kind {
	case kindRun:
		if runsBytes(len(c.runs)) > min(2*int(c.card), bitmapBytes) {
			if c.card <= arrayMax {
				c.convertToArray()
			} else {
				c.convertToBitmap()
			}
		}
	case kindArray:
		if c.card > arrayMax {
			c.convertToBitmap()
		}
	case kindBitmap:
		if c.card <= arrayMax {
			c.convertToArray()
		}
	}
	return c
}
```

Диаграмма переходов контейнеров в зависимости от типа:

```go
const (
	// arrayMax is the largest cardinality kept as a sorted array: above it the
	// fixed 8KiB of a bitmap costs less than 2 bytes per value.
	arrayMax = 4096
	// bitmapBytes is what a bitmap container always occupies.

)
```

## Rank/Select

В roaring bitmaps так же как и в обычной битмапе применяются операции rank и select:

- `rank(v int)` - это количество элементов, меньше или равных `v`
- `select(i int)` - i-тый по порядку элемент, присутствующий в множестве

На обычных битмапах rank реализуется через `popcnt`. На roaring bitmaps нам нужно посчитать количество элементов в каждом контейнере отдельно по своему - для битмап-контейнера через `popcnt`, для интервалов нужно из конечного индекса отнять начальный, для контейнера-массива просто получить количество элементов. Так же мы можем для каждого контейнера хранить префиксную сумму - ранк всех предыдущих контейнеров. При получении итогового ранка мы посчитаем ранк часла в найденном контейнере и сложим его с префиксной суммой. Единственная сложность в том, что нам нужно посчитать количество в хвостовом элементе. Для этого мы берем остаток от деления на 64 и берем правые биты "хвостового" числа. Таким образом, итоговая операция по сложности будет близка к `O(1)`. 

```go
// Popcount returns the number of set bits in a.
func Popcount(a []uint64) int {
	total := 0
	for _, w := range a {
		total += bits.OnesCount64(w)
	}
	return total
}

// PopcountPrefix returns the number of set bits among the first nbits bits of bm.
func PopcountPrefix(bm []uint64, nbits int) int {
	full := nbits / 64
	n := Popcount(bm[:full])
	if rem := nbits % 64; rem > 0 {
		n += bits.OnesCount64(bm[full] & (^uint64(0) >> uint(64-rem)))
	}
	return n
}
```

Реализация `select` довольно похожа на `rank`. Сначала нужно найти индекс контейнера, который имеет i-й элемент. Для этого мы возьмем массив префиксных сум и бин поиском найдем в нем больший, чем i элемент (нужно учесть, что в k+1-м элементе содержится k-тая префиксная сумма). Затем, мы возьмем в массиве ключей верхние биты, а нижние возьмем из найденного контейнера - вычтем из i префиксную сумму, чтобы получить значение, которое нужно найти в контейнере. Для массива - просто получить значение по индексу. Для интервала нужно пройтись по списку интервалов и вычитать из переданного индекса мощность каждого интервала, до тех пор пока индекс не станет меньше можности текущего интервала, после чего суммировать начало найденного интервала с полученным индексом. 

Для битмап контейнера расчет разделяется на 2 этапа. В битмап контейнере для начала нам нужно найти слово, в котором содержится нужный бит. Для этого мы последовательно пройдемся по всем словам и будем удалять из искомого индекса количество элементов в каждом слове до тех пор, пока количество индекс не станет меньше, чем количество элементов. 

После того, как мы нашли нужное нам слово, нужно найти в нем нужный бит - позицию i-го бита в слове. Применим снова трюк `w & (w-1)`. Вычитание единицы превращает младшую единицу в ноль, а все нули до нее в единицы. AND с исходным словом стирает эти единицы. В итоге обнуляется ровно младший установленный бит. После `rank` таких сбросов нужный бит становится младшим, и `TrailingZeros64` возвращает его позицию.

![](content/posts/roaring_bitmaps/clear_lowest_set_bit.svg)

```go
// SelectBit returns the position of the rank-th set bit of bm, counting from
// zero, or -1 when bm holds fewer bits than that.
func SelectBit(bm []uint64, rank int) int {
	for i, w := range bm {
		c := bits.OnesCount64(w)
		if rank < c {
			return i*64 + selectInWord(w, rank)
		}
		rank -= c
	}
	return -1
}

// selectInWord returns the position of the rank-th set bit within one word.
func selectInWord(w uint64, rank int) int {
	for ; rank > 0; rank-- {
		w &= w - 1
	}
	return bits.TrailingZeros64(w)
}
```

### Применение операций rank/select

1. Операции `rank` и `select` применяются в `succinct` структурах. Roaring bitmap там работает как **компактный индекс поверх разреженных данных** - когда необходимо разреженное множество данных отобразить на компактное применяется `rank`, когда нужно применить обратную операцию - по k-му значению определить номер строки - `select`. 
2. **Квантили и медиана**. Медиана множества `select(card / 2)`, p-й перцентиль - `select(p * card)`.
3. **Пагинация и OFFSET.** Выдать результаты запроса начиная с N-го - `select(N)` сразу даёт стартовое значение
4. **Кардинальность диапазона.** Сколько элементов в `[a, b]`: `rank(b) - rank(a - 1)`
5. **Перенумерация после удалений.** Если битмап хранит удалённые ID (tombstones), то после компакции новый ID вычисляется как `newId = oldId - rank_deleted(oldId)`

## Применение

`Roaring bitmaps` имеют широкое применение во многих современных базах данных, таких как

- ClickHouse - [битмар функции](https://clickhouse.com/docs/reference/functions/regular-functions/bitmap-functions), [Агрегатная функция groupBitmap](https://clickhouse.com/docs/reference/functions/aggregate-functions/groupBitmap)
- postgres ([расширение](https://github.com/ChenHuajun/pg_roaringbitmap))
- redis ([расширение](https://github.com/aviggiano/redis-roaring))
- Elasticsearch, OpenSearch - [bitmap_terms](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-bitmap-terms-query), [Агрегация](https://www.elastic.co/docs/reference/aggregations/search-aggregations-metrics-roaring-bitmap-aggregation)

Можно выделить несколько сценариев использования:

1. Построение OLAP запросов - сложные составные фильтры с логикой типа `A AND B OR NOT C`
2. Инвертированные индексы и полнотекстовый поиск - для каждого терма хранится множество документов, в которых он встречается, и, так же мы можем сделать запрос со сложно логикой
3. Отслеживание удалённых и изменённых записей (tombstones)
